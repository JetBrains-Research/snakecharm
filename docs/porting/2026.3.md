## Why `pluginSinceBuild` moved to 263

The 2026.2.1 binary installs on 263 and then fails at runtime: the verifier against
`IU-263.6259.32` reported 8 binary incompatibilities (6 `NoSuchFieldError`, 2 `NoSuchMethodError`,
items 18 and 20). The fixes recompile against 263-only signatures (the `PyOperatorReference`
constructor, `PyTypedDictType.getElementType(String, TypeEvalContext)`), so the new binary cannot load
on 262 either: `pluginSinceBuild`/`pluginUntilBuild` are `263`/`263.*` and `pluginVersion` is `2026.3.1`.

## 18. `PyReferenceBase` introduced; `myElement` moved and retyped — FIXED

263 inserts `PyReferenceBase` under `PyReferenceImpl` (and under `PyOperatorReference`, which no longer
extends `PyReferenceImpl`). The field moved with it, and its type changed:

```
262: PyReferenceImpl  { protected final PyQualifiedExpression myElement; }
263: PyReferenceBase  { protected final PyQualifiedElement    myElement; }   // PyReferenceImpl.getElement() still returns PyQualifiedExpression (covariant)
```

Kotlin compiles `myElement` to `getfield <our class>.myElement:LPyQualifiedExpression;`. On 263 no
field with that descriptor exists, so the verifier reports `NoSuchFieldError`, 6 times:
`SmkPyReferenceImpl` (2), `SmkSLInitialReference` (2), `SmkPyQualifiedReference`,
`SmkRuleOrCheckpointNameReference`. On 263 the one case that needed `PyQualifiedExpression`
(`SmkPyReferenceImpl.kt:69`) also fails to compile. Every use now goes through the `element` getter,
which does not depend on where the field is declared or on its type.
`SmkSLInitialReference.getElement()` casts `super.getElement()`. `myContext` moved too, but its type
did not change and the JVM resolves field references through superclasses, so it still links (the
verifier does not flag it).

## 21. Deprecated and scheduled-for-removal APIs — FIXED, except one

- `PythonLanguageLevelPusher.getLanguageLevelForVirtualFile` is `@Deprecated(forRemoval = true)`.
  Replaced with what its body does: `PyLanguageFacade.INSTANCE.getEffectiveLanguageLevel(project, file)`.
  The facade (`intellij.python.parser`) is abstract and implemented by `PyLanguageFacadeImpl`.
  - **Rejected alternative:** `PythonLanguageLevelPusher.getEffectiveLanguageLevel(project, file)`.
    `PyLanguageFacadeImpl` ends up there, so it behaves the same today, and it was briefly used on this
    branch. But the whole `PythonLanguageLevelPusher` class is `@ApiStatus.Internal` (in 262 as well).
    That swaps a deprecated call for an internal one: the verifier listed it in
    `internal-api-usages.txt`. It also ties us to the backend implementation, bypassing the facade.
  - **Remaining risk:** `PyLanguageFacade` is `@ApiStatus.Experimental` (as is `PyAnyType`, item 22),
    so re-check it on each EAP. Both exist with the same signatures in 262.
  - **Lesson:** "behaviour-equivalent" is not enough when picking a replacement. Check the API status
    of the replacement's *class* too, not just of the method.
- `DaemonCodeAnalyzer.restart()` / `restart(PsiFile)` → `restart(Object reason)` /
  `restart(PsiFile, Object reason)`. The old overloads delegate with the reason `"Global restart"`, so
  the reason is for diagnostics only.
- `com.jetbrains.python.packaging.pyRequirement` moved to `com.intellij.python.requirements.pyRequirement`
  (`replaceWith` in its `kotlin.Deprecated`). Only the import changes. The function still returns
  `com.jetbrains.python.packaging.PyRequirement`, and the new package is 263-only.
- **Left as is:** `PyConfigurableInterpreterList.getInstance(project).getAllPythonSdks()` in
  `SmkFrameworkSettingsPanel`. It was already deprecated on 262, and it is the only verifier
  deprecation left on 263. It delegates to `getAssignablePythonSdks`, which is `@ApiStatus.Internal`
  and filters by eel machine and run-config compatibility. No public replacement exists, and
  re-deriving the list from `ProjectJdkTable` would silently drop that filtering.
- The verifier also listed `EditorNotifications.Provider` against the released 2026.2.1. The current
  sources do not use it: `SmkSupportDisabledBanner` is already an `EditorNotificationProvider`, and the
  263 verifier run no longer reports it.

Test sources needed two adjustments of their own in `PythonMockSdk`.
`com.jetbrains.python.sdk.PythonSdkUtil.SKELETON_DIR_NAME` was removed, and the constant now lives
only in `com.jetbrains.python.sdk.legacy.PythonSdkUtil`. `VirtualEnvSdkFlavor` is now annotated with
the `RequiresOptIn(ERROR)` marker `@PyInternalExecApi`. The mock SDK keeps that flavor, because it
is the platform-independent one that `isValidSdkPath()` accepts. `@OptIn` is acceptable here because
this is test code only.

## 22. `python.type.any` is on by default: `getType` must not return `null` — FIXED (6 failures)

```
java.lang.AssertionError: A Python type was `null` while `Any`/`Unknown` support was enabled.
element : com.jetbrains.snakecharm.stringLanguage.lang.psi.SmkSLSubscriptionExpressionImpl
```

`TypeEvalContextImpl.getType(PyTypedElement)` now passes every result through
`PyAnyType.validate(type, element)`. That check throws in tests, EAP and internal mode, and logs an
error otherwise. With the registry flag `python.type.any` on, a `null` type is an error. With it
off, a `PyAnyType` is an error. The flag's `defaultValue` flipped from `false` (262) to `true` (263),
which is why 2026.2 was green. The platform's own `PySubscriptionExpressionImpl`/`PyReferenceExpressionImpl`
now return `PyAnyType.unknown` where they used to return `null`.

`PyAnyType.unknown` is the right value in both modes: it is `Unknown.INSTANCE` with the flag on and
`null` with it off. `SmkSLSubscriptionExpressionImpl`, `SmkSLSubscriptionIndexKeyExpressionImpl` and
`SmkReferenceExpressionImpl` return it instead of `null`. The last one is not covered by any
scenario, but the same assertion would hit it. Every consumer checks the type with `is Smk...Type`,
which `Unknown` fails just as `null` did, so "not supported yet" still means no reference and no completion. The
other `getType` implementations (`SmkRuleImpl`, `SmkCheckPointImpl`, `SmkUseImpl`, the args sections,
`SmkWildcardFakePsiElement`) already return non-null types. `PyAnyType` exists with the same
signatures in 262, but it is `@ApiStatus.Experimental`, so re-check it on each EAP.

## 23. Python keyword completion no longer fires in lambda parameter lists — FIXED in tests (31 failures)

`Completion for lambda parameter names in specific sections` failed in two ways. "No completion for lambda
invocations" (26) failed with `Completion list not initialized`, and "Completion in section with tail
text for the last parameter" (5) failed with `Completion resulted in a single possible variant`.

**The plugin's behaviour did not change.** On 262, `PyKeywordCompletionContributor` guarded its
`not`/`lambda`/`True`/`False`/`None` providers with `NOT_PARAMETER_OR_DEFAULT_VALUE`, which accepted a
lambda parameter position. So the popup always held a few unrelated Python keywords besides
SnakeCharm's items. On 263 that filter is gone, and the providers exclude
`IS_PARAMETER_NAME`/`IS_DECLARATION_NAME`. As a result, there is now one variant: `yield` where
SnakeCharm offers nothing, or SnakeCharm's single last parameter. The light fixture auto-inserts a
single variant and opens no lookup. Both outlines had passed only because of the extra Python keywords.

- New step `I invoke autocompletion popup without inserting a single variant`
  (`CompletionResolveSteps`). It turns off `CodeInsightSettings.AUTOCOMPLETE_ON_CODE_COMPLETION` for
  one invocation, so the list can still be asserted. "No completion for lambda invocations" uses it,
  with its `shouldn't contain` assertions unchanged.
- The tail-text outline now asserts the auto-inserted text (`..., threads: #`), which still checks
  both the variant and its `ColonAndWhiteSpaceTail`. What it no longer exercises is *selecting* the
  item from a popup, because on 263 no popup opens.

Lesson, similar to [2026.2 finding 13](2026.2.md#13-snakemake-with-disabled-framework-did-not-disable-it--fixed): **a completion scenario can depend on unrelated
platform variants being present.** If a platform change removes them, the scenario fails even though
the plugin's own completion did not change.
